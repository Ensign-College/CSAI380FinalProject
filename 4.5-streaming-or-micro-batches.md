# 4.5 Block Project: Streaming or Micro-batches

🚧 DRAFT — not yet tested end-to-end

## Purpose:

Add event flow to your project. You will install Kafka in Kubernetes with Helm, create a topic, and prove the full path Producer → Kafka topic → Consumer — first with the console scripts, then with real STEDI application events generated by its built-in simulation. Finally you will reason about what you built: is this workload batch, micro-batch, or streaming, and why does that matter?

## AI Ops in This Assignment:

- **(a) Use an agent to do the ops.** Kafka has a steep CLI: let an agent draft your `kafka-topics.sh` and console producer/consumer commands, explain broker DNS names and consumer groups, or diagnose a connection refused from the client pod when you paste in the error and your service names. Verify each answer against the cluster — run the command, read the output, re-prompt with what actually happened. Captured consumer output also makes a good agent exercise: paste a few events in and ask the agent to characterize them before you write your own analysis (then make the analysis yours).
- **(b) Build infrastructure that AI operations run on.** Event streams are how AI systems see the world in real time. The STEDI risk events flowing through your topic are exactly the kind of signal a model consumes — for real-time scoring, online feature computation, or anomaly detection — and the batch/micro-batch/streaming classification you write this week is the same decision that determines whether a model scores events as they happen or hours later. Kafka topics are also the standard feed into online feature stores and the standard transport for inference requests and results at scale.

## Instructions:

1. Continue in your final-project repository. Copy this week's starter files:
   1. [starter/helm/kafka-values.yaml](starter/helm/kafka-values.yaml) → `helm/`
   2. [starter/k8s/kafka/kafka-client.yaml](starter/k8s/kafka/kafka-client.yaml) → `k8s/kafka/`
   3. [starter/k8s/kafka/stedi-kafka-patch.yaml](starter/k8s/kafka/stedi-kafka-patch.yaml) → `k8s/kafka/`
   4. [starter/k8s/kafka/logging-consumer.yaml](starter/k8s/kafka/logging-consumer.yaml) → `k8s/kafka/`

> **If you parked your namespace:** the simulation needs the app stack — `kubectl scale deployment stedi --replicas=1 -n <your-namespace>` and `kubectl scale statefulset redis-stedi --replicas=1 -n <your-namespace>`. Airflow and MySQL can stay parked this week.

2. Install Kafka with Helm using the command in the header of [starter/helm/kafka-values.yaml](starter/helm/kafka-values.yaml). Note the warning in that file: single-broker PLAINTEXT Kafka is a teaching configuration — never run it that way in production.

3. Create a topic and test it with the console scripts:
   1. Apply [starter/k8s/kafka/kafka-client.yaml](starter/k8s/kafka/kafka-client.yaml) and exec into the pod.
   2. Create a topic named `customer-risk` with `kafka-topics.sh --create`.
   3. Send dummy events with `kafka-console-producer.sh` targeting the topic.
   4. In a second terminal, consume them with `kafka-console-consumer.sh --from-beginning`. Capture both terminals for your evidence file.

4. Connect STEDI to Kafka:
   1. Complete the `# TODO(student)` in [starter/k8s/kafka/stedi-kafka-patch.yaml](starter/k8s/kafka/stedi-kafka-patch.yaml) (add the `KAFKA_RISK_TOPIC` variable) and apply the patch.
   2. Toggle the simulation on to generate live simulated user data: `curl -X POST http://<stedi-service>/simulation` (check it with a GET to the same path; a DELETE turns it off).
   3. Re-run `kafka-console-consumer.sh` against `customer-risk` and capture live STEDI events arriving.

5. Deploy a logging consumer/sink: edit the placeholders in [starter/k8s/kafka/logging-consumer.yaml](starter/k8s/kafka/logging-consumer.yaml), apply it, and capture `kubectl logs -f` output showing events being received.

6. In `week-4-evidence.md`, alongside your captures, write a short analysis: is the STEDI risk-event use case batch, micro-batch, or streaming? Define all three, justify your classification, and name one scenario where each of the other two models would be the better choice.

7. Add an **AI Ops reflection** section to `week-4-evidence.md`: (a) one concrete step where an AI agent helped this week (prompt, output, how you verified it against the cluster); (b) describe one way an AI system would consume the `customer-risk` event stream — real-time scoring, online features, anomaly detection — and what that consumer would need from the infrastructure you built.

8. Update `architecture.md`: the diagram now shows STEDI → Kafka topic → logging consumer as implemented.

> **Parking:** turn the simulation off (`curl -X DELETE http://<stedi-service>/simulation`), then `kubectl scale deployment,statefulset --all --replicas=0 -n <your-namespace>`. Your topic and its events stay on Kafka's PVC — week 5 consumes this exact stream.

9. **Submit** the link to your GitHub repository to Canvas.
