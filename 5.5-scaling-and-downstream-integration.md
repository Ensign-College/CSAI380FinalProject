# 5.5 Block Project: Scaling and Downstream Integration

🚧 DRAFT — not yet tested end-to-end

## Purpose:

Close the loop: deliver your Kafka events to a downstream destination and prove the system scales. You will deploy a MySQL consumer/sink that lands STEDI risk events in the operational data store in near real-time, verify data integrity with ad-hoc SQL, and then experiment — stop the consumer and watch lag build, scale it up and watch the backlog drain. The point is integration and observation, not Kafka mastery: increased capacity in one place creates increased responsibility elsewhere in the system.

## AI Ops in This Assignment:

- **(a) Use an agent to do the ops.** The scaling experiment is an agent loop you run by hand: observe (consumer lag), hypothesize, act (scale), verify (lag drains, no duplicates). Bring an AI agent into it — ask it to draft the upsert for the `# TODO(student)`, write your duplicate-check and analytical SQL, or interpret the `kafka-consumer-groups.sh --describe` output you paste in (ask it to explain the LAG column before you record your baseline). As always, the agent proposes and the cluster disposes: verify every claim with a real command before you write it down as an observation.
- **(b) Build infrastructure that AI operations run on.** This week's lessons are the operating constraints of production AI. Consumer lag is feature staleness: a model scoring on events that are minutes behind is making predictions about the past. Scaling consumers against partition counts is exactly how inference and feature-computation workers scale. And your idempotent upsert is the mechanism that keeps feature tables and training data correct through replays and crashes — exactly-once results in an at-least-once world.

Build the `event_key` from the message's partition and offset and use an upsert (`INSERT ... ON DUPLICATE KEY UPDATE`) so replayed messages never create duplicate rows.

3. Deploy the sink:
   1. Create the script ConfigMap and apply the deployment as described in the header of [starter/k8s/kafka/mysql-sink-consumer.yaml](starter/k8s/kafka/mysql-sink-consumer.yaml), after replacing the placeholders.

4. Check data integrity with ad-hoc SQL in `week-5-evidence.md`:
   1. A duplicate check proving no event was inserted twice, e.g. `SELECT event_key, COUNT(*) FROM risk_events GROUP BY event_key HAVING COUNT(*) > 1;` (expect zero rows).
   2. One query of your own design that tells you something interesting about the events (rate per minute, distribution by payload field, etc.).

5. Run the scaling experiment and record each observation:
   1. Baseline: monitor the topic's rate of consumption with `kafka-consumer-groups.sh --describe --group mysql-sink` from the kafka-client pod. Record the LAG column.

   3. Restart and scale up: `kubectl scale deployment mysql-sink-consumer --replicas=3`. Record how partitions are distributed across the consumers in the group and how quickly the lag drains. Note: with a single-partition topic, explain why extra replicas sit idle — and what you would change to let them help.
   4. Re-run the duplicate check from step 4 after all scaling activity — the upsert should have kept the table clean.

Add an **AI Ops reflection** section to `week-5-evidence.md`: (a) one concrete step where an AI agent helped this week — ideally inside the scaling experiment's observe → hypothesize → act → verify loop — with the prompt, output, and how you verified it; (b) explain what consumer lag would mean for an AI system consuming these events (feature staleness, stale predictions) and how the scaling and idempotence techniques you practiced protect it.
