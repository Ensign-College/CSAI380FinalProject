# 3.5 Block Project: Working ETL Pipeline

🚧 DRAFT — not yet tested end-to-end

## Purpose:

Build a real batch ETL pipeline: Apache Airflow (installed in Kubernetes with Helm) extracts a CSV from a Google Cloud Storage bucket, transforms it, and loads the result into the MySQL operational data store you deployed in week 2. By the end of this week your project moves and reshapes real data on a schedule — the heart of the final project — and you will have practiced the troubleshooting loop (Observe → Diagnose → Remediate → Verify) that every data engineer lives in.

## AI Ops in This Assignment:

- **(a) Use an agent to do the ops.** The Observe → Diagnose → Remediate → Verify cycle you practice this week *is* an agent loop — the same loop an AI agent runs when you hand it a problem. Use that deliberately: paste a failing Airflow task log or a DAG import error into an agent and ask for a diagnosis, ask it to draft the pandas transform for the `# TODO(student)` step, or have it explain what makes a load idempotent before you implement one. Then close the loop yourself — rerun the DAG and verify in MySQL. An agent's remediation that you haven't verified is just a hypothesis.
- **(b) Build infrastructure that AI operations run on.** Orchestrated data pipelines are how AI systems eat: Airflow (and its descendants) schedule the data-prep, feature-engineering, training, evaluation, and batch-inference jobs behind production ML. Your transform step — dropping the row with the missing country code — is data quality in miniature, and in an AI context data quality *is* model quality: bad rows in means bad predictions out. Idempotent loads are what make retraining pipelines safe to re-run.

## Instructions:

1. Continue in your final-project repository. Copy this week's starter files:
   1. [starter/helm/airflow-values.yaml](starter/helm/airflow-values.yaml) → `helm/`
   2. [starter/dags/etl_pipeline.py](starter/dags/etl_pipeline.py) → `dags/`
   3. [starter/data/country-codes-sample.csv](starter/data/country-codes-sample.csv) → `data/`

> **If you parked your namespace:** this week's load target is week 2's MySQL — un-park it with `kubectl scale statefulset mysql --replicas=1 -n <your-namespace>` (plus `redis-stedi` and the `stedi` deployment if you want the app up). The `stedi` database and your week-2 rows are still on the PVC.

2. Stage the source data: upload the CSV to the ETL bucket Terraform created in week 1:
   `gsutil cp data/country-codes-sample.csv gs://<project-id>-<your-namespace>-etl/`

3. Install Airflow 3 with Helm:
   1. Create the webserver secret: `kubectl create secret generic airflow-webserver-secret -n <your-namespace> --from-literal=webserver-secret-key=$(openssl rand -hex 16)`
   2. Complete the `# TODO(student)` in [starter/helm/airflow-values.yaml](starter/helm/airflow-values.yaml): point `gitSync` at your assignment repository so Airflow loads your DAG.
   3. Install using the commands in the values file header, then port-forward to the Airflow UI and log in: `kubectl port-forward svc/airflow-api-server 8080:8080 -n <your-namespace>`

4. Finish and activate the DAG in [starter/dags/etl_pipeline.py](starter/dags/etl_pipeline.py):
   1. Set `GCS_BUCKET` to your bucket.
   2. Implement the `# TODO(student)` **transform** step: keep only the country code, official English name, capital, continent, currency name, and internet TLD columns, and drop rows missing a country code (the sample data contains one on purpose).
   3. Implement the `# TODO(student)` **load** step so reruns do not duplicate rows (idempotent load).
   4. In the Airflow UI, create the `stedi_mysql` connection pointing at `mysql-0.mysql.<your-namespace>.svc.cluster.local` (password from your `mysql-secrets` secret — enter it in the UI, never commit it).
   5. Unpause `stedi_etl_pipeline` and trigger a run.

5. Demonstrate the working pipeline in `week-3-evidence.md`:
   1. Screenshot of a successful (all-green) DAG run in the Airflow UI.
   2. Query output from MySQL showing the loaded `country_codes` rows, including proof the invalid row was dropped.
   3. Trigger the DAG a second time and show the row count did not change (idempotence).
   4. Describe one failure you hit along the way and how you worked through Observe → Diagnose → Remediate → Verify.
   5. Add an **AI Ops reflection**: (a) one concrete step where an AI agent helped — ideally inside your troubleshooting loop from the previous item — with the prompt, the output, and how you verified it; (b) how this week's skill shows up in AI infrastructure: name one job an ML pipeline would schedule with an orchestrator like Airflow and where it would fit in your architecture.

6. Update `architecture.md` to **v3**: the diagram now shows GCS → Airflow (Extract → Transform → Load) → MySQL as implemented.

> **Parking:** Airflow idles expensively. Between sessions, `kubectl scale deployment,statefulset --all --replicas=0 -n <your-namespace>` — your DAG-run history (Airflow metadata DB) and MySQL rows survive on their PVCs.

7. **Submit** the link to your GitHub repository to Canvas.
