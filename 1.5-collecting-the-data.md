# 1.5 Block Project: Collecting the Data

🚧 DRAFT — not yet tested end-to-end

## Purpose:

Begin your seven-week final project by designing its architecture and deploying your first working Kubernetes workload. You will produce Project Architecture v1, provision your own cloud resources with Terraform, and deploy the STEDI application to GKE using a GitHub Actions pipeline. Everything you build in weeks 2–6 extends what you create this week, so the goal is a solid, version-controlled foundation: infrastructure as code, a repeatable deployment, and a clear picture of where the data will flow.

## Instructions:

1. Create a new GitHub repository for your final project and clone it. All work for assignments 1.5 through 5.5 lives in this repository — submit the same repository link each week.

2. Get the STEDI application source: copy the STEDI project provided by your instructor into the root of your repository so its `Dockerfile` sits at the repository root. This is the application you will build, containerize, and deploy all semester.

3. Copy the starter files from this assignment into your repository, keeping the same layout:
   1. [starter/.gitignore](starter/.gitignore) — commit this first; it keeps Terraform state and credentials out of git.
   2. [starter/terraform/main.tf](starter/terraform/main.tf), [starter/terraform/variables.tf](starter/terraform/variables.tf), [starter/terraform/outputs.tf](starter/terraform/outputs.tf)
   3. [starter/k8s/stedi/stedi-deployment.yaml](starter/k8s/stedi/stedi-deployment.yaml), [starter/k8s/stedi/stedi-service.yaml](starter/k8s/stedi/stedi-service.yaml)
   4. [starter/.github/workflows/build-deploy.yaml](starter/.github/workflows/build-deploy.yaml)

4. Provision your student-scoped infrastructure with Terraform:
   1. In `terraform/`, create a `terraform.tfvars` with your `project_id`, `region`, and `student_namespace` (use `<your-netid>-stedi`).
   2. Complete the `# TODO(student)` in [starter/terraform/main.tf](starter/terraform/main.tf): add the `stedi-dev-sa` Kubernetes service account the STEDI deployment references.
   3. Run `terraform init`, `terraform plan`, and `terraform apply`. Record the three outputs — you need them in the next steps.

5. Deploy the STEDI application:
   1. Replace every `<angle-bracket>` placeholder in the `k8s/stedi/` manifests with your values.
   2. Configure the GitHub Actions secrets listed at the top of [starter/.github/workflows/build-deploy.yaml](starter/.github/workflows/build-deploy.yaml), set `STUDENT_NAMESPACE`, and complete its `# TODO(student)` so the workflow deploys the image it just built.
   3. Push to `main` and verify the workflow builds the STEDI image from your repository's Dockerfile, pushes it to Artifact Registry, and deploys to your namespace.
   4. Prove the workload is healthy: capture the output of `kubectl get pods -n <your-namespace>`, `kubectl describe deployment stedi -n <your-namespace>`, and `kubectl logs` from the STEDI pod in a `week-1-evidence.md` file in your repository.

6. Write **Project Architecture v1** in an `architecture.md` at the root of your repository. Use the course reference diagram as your guide: [docs/images/final-project-architecture.png](docs/images/final-project-architecture.png). It must include:
   1. A Mermaid diagram showing the expected end-to-end data flow: data source → STEDI application → Redis → Kafka → ETL/processing → MySQL → analytical destination (object storage).
   2. The application's data source and operational data store.
   3. Where Kafka, the ETL pipeline, object storage, and the analytical destination will eventually fit.
   4. A brief explanation of the purpose of each component.
   5. Two technical risks or unknowns you anticipate.
   6. What you will add each week from week 2 through week 6 (a short project plan).

7. Write a retrospective section at the bottom of `architecture.md`: what do you need help with, and what do you lack understanding of after this week?

8. **Submit** the link to your GitHub repository to Canvas.
